# 运行环境与配置

产品口径：当前以**单用户**部署为主，但配置按 dev / local / prod 三档区分，
并为多用户/对外 API 预留了开关。默认值全部保持原有本地行为。

## 环境分档

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `FIL_ENV` | `local` | `dev` / `local` / `prod`；未知值回退 `local` |
| `FIL_DATA_DIR` | local/prod: `output/data`；dev: `output/dev/data` | 数据资产目录（DuckDB、审计、缓存） |
| `FIL_FIG_DIR` | local/prod: `output/figures`；dev: `output/dev/figures` | 图表产物 |
| `FIL_RES_DIR` | local/prod: `output/results`；dev: `output/dev/results` | 报告与冒烟结果 |
| `FIL_ENV_FILE` | 未设置 | 指定 `.env` 路径；仅在该变量存在时读取，不覆盖已有环境变量 |

生产环境建议显式设置 `FIL_DATA_DIR` 到独立磁盘卷；`local` 保持仓库内路径，
不改变现有 CLI / Web 用法。

## 启动方式与入口

```powershell
uv sync --locked
uv run --locked market-research --port 8877   # 原有方式
.\scripts\start.ps1                            # 一键启动（默认 8760）
.\scripts\start.ps1 -Port 8877 -NoWorker
```

- 安装后提供短别名 `fil`（研究 CLI）、`fil-serve`（Web）、`fil-worker`、`fil-sync`，
  与 `market-research` / `market-research-cli` 等原有入口完全等价，旧入口保留。
- `scripts/start.ps1` 优先调用 `.venv\Scripts\market-research.exe`，缺失时回退
  `uv run --locked`；默认端口、监听地址、数据目录不变。
- `.env` 由 `market_research.envfile` 读取，仅当 `FIL_ENV_FILE` 指向文件时生效；
  启动脚本在项目根存在 `.env` 时自动设置该变量。逐行 `KEY=VALUE`，支持整行
  `#` 注释、`export ` 前缀与成对引号；已存在的环境变量优先，不会被覆盖。
- 不需要手动设置 `PYTHONPATH`：`uv run` 与安装后的入口都使用已安装的 `src` 包；
  只有直接用系统 Python 从仓库运行且未安装时才需要 `PYTHONPATH=src`。

实测冷启动（Windows 本机）：Web 到 `/api/health` 冷缓存约 4.4 秒、热缓存
约 2.2～2.3 秒，耗时主要在 pandas 与 FastAPI 导入（各约 1.1 秒），没有安全的
进一步压缩空间；`fil --help` 约 0.5 秒（经 `uv run` 约 0.7 秒），
`fil-worker --help` 约 1.1 秒。

## 访问控制（P2-24）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `FIL_ACCESS_CONTROL` | `off` | `off` = 单用户无认证；`token` = 校验 API 令牌 |
| `FIL_API_TOKENS` | 空 | `token` 模式下允许的令牌，逗号分隔；支持 `租户:令牌` |

- `token` 模式下，业务接口需带 `Authorization: Bearer <token>` 或 `X-API-Key`；
  未授权返回 401。
- `/`、`/api/health`、`/api/ready`、`/api/disclosure` 与静态资源保持公开，
  便于探针与页面加载；对应的 `/api/v1/health`、`/api/v1/ready`、`/api/v1/disclosure` 同样公开。
- 启动日志会打印当前模式（单用户 / 令牌模式）。
- 多用户升级还需：把任务与结果缓存按 `Identity.tenant` 分区、按用户配额，
  以及用户的注册/登录体系；当前只预留了身份上下文与开关，不会强制登录。

## 数据抓取（P2-29）

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `FIL_HTTP_MAX_RPS` | `8` | 全进程抓取请求上限（请求/秒）；`<=0` 关闭限流 |
| `FIL_HTTP_TIMEOUT` | `30` | 单次抓取超时秒数，线程级生效；`0` 表示不限制 |
| `FIL_DATA_STALE_DAYS` | `10` | 数据末日超过该天数标记 stale；同步缓存 `info.data_end` 落后 `through` 超过该天数时 `sync.cached()` 视为未就绪，不再把滞后行情当新鲜数据 |
| `FIL_NAV_DEGRADED_POLICY` | `reject` | 总回报口径失败时 `reject` 或 `allow_cum`（后者必须显式标注） |

重试为最多 4 次、指数退避（基准 1.2 秒 + 抖动）；`ValueError`/`KeyError`/`TypeError`/`AttributeError` 与 `ProviderContractError` 不重试。

## 存储、任务与队列

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `FIL_STORAGE_LOCK_TIMEOUT` | `10` | DuckDB 文件锁最长等待秒数；超时抛 `StorageBusy` |
| `FIL_MAX_JOBS` | `2` | 同时运行的分析子进程数 |
| `FIL_QUEUE_LIMIT` | `100` | `queued + running` 任务总上限，超出返回 429 |
| `FIL_JOB_TIMEOUT` | `900` | 单任务超时秒数 |
| `FIL_JOB_ATTEMPTS` | `3` | 进程中断后的最大尝试次数 |
| `FIL_JOB_TERMINAL_TTL` | `86400` | 持久店 `done`/`error` 任务保留秒数（下限 60），超期物理删除；内存店仍是 30 分钟 `JOB_TTL_SEC`，只服务单进程回调 |
| `FIL_JOB_QUEUED_TTL` | `3600` | `queued` 排队有效期秒数（下限 60），超期转 `error` 并记「排队超时」，避免 worker 久停后队列永久 429 |
| `FIL_JOB_DRAIN_GRACE` | `30` | 取消/超时后旧子进程排水的名额占位秒数；`0` 关闭。纯时间衰减，无需显式释放 |
| `FIL_JOB_WORKERS` | `0` | 单任务模型并行进程数；`0` = 自动 `min(模型数, max(1, CPU-1))` |
| `FIL_JOB_WORKERS_MAX` | `0` | 模型并行全局上限；`0` = 不限 |
| `FIL_JOB_MEMORY_MB` | `0` | 单任务内存上限（MB）；`0` = 不限。POSIX 用 `RLIMIT_AS`，Windows 用 Job Object |
| `FIL_START_DATE` | 未设置 | 固定基金分析起点，覆盖滚动默认值 |
| `FIL_AUTO_SERVICES` | `1` | API 自动拉起 worker；`0` 交由外部进程管理 |
| `FIL_SYNC_ENABLED` / `FIL_SYNC_TIME` | `1` / `18:30` | 同步开关与北京时间；`0` 同时拦截常驻 `serve()` 与 `--once` 单次执行 |
| `FIL_PREDICTION_SETTLE_ENABLED` | `1` | worker 内置预测台账结算开关；`0` 关闭，改用外部计划任务或手动 CLI |
| `FIL_PREDICTION_SETTLE_MINUTES` | `60` | 结算间隔（分钟，下限 1，配置错误回退 60）；子进程独立运行，失败不影响任务队列 |
| `FIL_CORS_ORIGINS` | 空 | 逗号分隔跨域来源 |

并发名额按「运行中 + 刚异常终态的排水占位」计算：取消或超时后旧子进程仍有 `FIL_JOB_DRAIN_GRACE` 秒被回收，名额不会瞬时释放造成 `max_jobs+1` 个写进程；占位随时间自动衰减，无需显式释放计数点。`/api/result` 对取消返回 409 + `reason=cancelled`，排队超时与真实失败分别带 `reason=queue_timeout` / `failed`，调用方无需靠错误文案猜测终态原因。

`StorageBusy` 由 FastAPI 异常处理映射为 **503**（`ok=false`、`field=storage`、可读原因与 `retry_after_s`），表示存储锁暂时被同步或其它进程占用，客户端可稍后重试；`/api/v1/corr` 等路由不会再用通用 500 吞掉它。

端点与字段契约见 [数据源供应商契约](数据源供应商契约.md)。

对外接口以 `/api/v1` 为正式路径，旧 `/api` 保留兼容且两套路径同时出现在 `/openapi.json`；所有响应带 `X-API-Version: 1`，关键响应由 `JobResponse`/`ResultResponse`/`HealthResponse`/`ReadyResponse` 固定字段。

## 日志与保留

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `FIL_LOG_DIR` | `FIL_DATA_DIR` | 应用与进程日志目录 |
| `FIL_LOG_MAX_BYTES` | `5000000` | 单个应用日志文件上限（字节） |
| `FIL_LOG_BACKUPS` | `3` | 轮转保留份数（`*.1` … `*.N`） |
| `FIL_LOG_LEVEL` | `INFO` | 应用日志级别 |
| `FIL_LOG_RETENTION_DAYS` | `7` | `job-{id}.log` 等任务日志按天清理 |
| `FIL_CHECKPOINT_DIR` | `FIL_DATA_DIR/checkpoints` | 阶段检查点目录 |
| `FIL_CHECKPOINT_TTL_DAYS` | `2` | 检查点保留天数，超期目录自动删除 |

日志文件：API `api.log`、worker 监督进程 `worker.log`、worker 子进程输出 `worker-process.log`、同步 `sync.log`/`sync-process.log`、单任务 `job-{id}.log`。应用日志采用“追加后立即关闭句柄”的轮转方式，避免 Windows 下常驻句柄阻塞目录重命名/删除；子进程 stdout 重定向文件在进程存活期间不轮转，下次启动时生效。失败任务超时重试时会复用指纹一致的阶段检查点，指纹不一致或文件损坏则从零执行。

设置 `FIL_JOB_MEMORY_MB` 后超出内存上限的任务会失败并给出可读原因：POSIX 通常抛 `MemoryError`；Windows 由 Job Object 终止进程，最终表现为进程退出并按 `FIL_JOB_ATTEMPTS` 重试。

## 真实数据冒烟与 CI（P2-35）

```bash
python scripts/smoke_real.py --code 110022 --out output/results/smoke
```

手动触发，覆盖抓取→面板→分析→报告；失败时输出目录下的 `smoke_result.json` 会标记
`failure_class = data_source | logic`。CI（`.github/workflows/ci.yml`）只跑
全量单测（407 项，2026-11-07 执行）与 Python/JavaScript 语法检查，不跑真实数据。

## 就绪检查

- `/api/v1/health`：仅存活探针，返回 pid、uptime、`environment`、`access_control`、`api_version`（旧 `/api/health` 等价）。
- `/api/v1/ready`：检查 DuckDB、worker pid、任务状态分布、估值面板最近同步日期
  （`2×FIL_DATA_STALE_DAYS`）、锁统计与资源上限（`checks.limits`：CPU、并发/队列、超时、
  模型并行与内存上限）；存储/worker/队列异常返回 503，仅同步过期返回 200 + `degraded`（旧 `/api/ready` 等价）。
- `/api/v1/disclosure`：返回与 Web/报告一致的免责与数据来源披露，不受访问控制限制（旧路径等价）。
